## 总览

项目在 **题库系统** 和 **L1课程** 两个板块已达到生产级质量，但 **L3-L6课程内容深度** 和 **学习路径引导** 存在明显的短板。以下按六个维度逐项分析。

| 维度 | 当前评分 | 核心问题 |
|------|----------|----------|
| 课程内容质量 | ⭐⭐⭐ | L3-L6 内容过于骨架化，缺少深度讲解和练习题量 |
| 结构逻辑 | ⭐⭐⭐⭐ | 双层体系（课程+冲刺页）设计合理，但两套内容缺乏联动 |
| 用户学习路径 | ⭐⭐ | 无进度追踪、无个性化推荐、新手不知道从哪里开始 |
| 互动性 | ⭐⭐⭐ | 有交互式实验和代码追踪器，但覆盖面不均且缺少编程实操 |

| 技术性能 | ⭐⭐⭐⭐ | 懒加载+代码分割到位，整体bundle 9.5MB偏大但有优化空间 |

## 一、课程内容质量

### 现状

**C++ L1 — 优秀（16/16课实质完成）**

每课 627-1130 行，包含自研交互式组件（QuizCard、DeviceItem、CodePart）、休息幻灯片（点击揭示）、丰富的视觉教学元素。课程叙事有「导入→概念→实操→避坑→冲刺」完整弧线。

**C++ L2 — 中等（4课充实 / 4课中等 / 8课轻量）**

第1-4课（RAM/IP、ASCII、类型转换、Switch）内容充实（444-1080行），使用了DigitLab等交互组件。第5-16课使用了CppLessonShell但内容量偏少（168-257行），缺少与C++实际编程的结合。

**C++ L3-L6 — 骨架化（64课均为180-226行）**

统一使用 CppLessonShell 的5段式模板：课程导入→概念讲解→核心代码→进阶/迁移→练习与作业。每课有一个交互式Lab（滑块控制的数值实验台），但：
- 概念讲解仅为2-3个段落，缺少多角度解释和类比
- 练习题统一3道 MiniQuiz（问答式），无编程实操题
- 没有分层难度（基础/进阶/挑战），所有学生看同一份内容
- 比如L5「素数大筛选」讲埃氏筛，却没有任何让学生手写代码的环节

**Python 基础（F1-F7）— 良好**

每课 619-1127 行，内容充实、叙事性强。F1 用「魔法语言」类比引入，视觉丰富。但代码示例偏展示型，缺少让学生修改变量观察结果的互动环节。

**Python 进阶（8个Project）— 中等**

BinarySearchProject 604行、EncryptionProject 922行、SortingProject 2229行（最丰富）、MorseProject 426行。项目之间内容深度不均，SortingProject一枝独秀。

**8个等级冲刺页（L1-L8）— 良好**

CourseLevel1-8 每页 810-1701 行，包含多标签页（概览/专题/代码追踪/避坑/技巧/练习）。L1最丰富（1453行+15题练习测验），L7/L8逐渐变薄（~900行）。

### 问题清单

| # | 问题 | 严重度 | 影响范围 |
|---|------|--------|----------|
| P1 | L3-L6 课程内容严重骨架化，64课平均仅~200行 | 🔴 高 | 覆盖 C++ 三级到六级全部学生 |
| P2 | 缺少编程实操题，学生看完概念没有动手写代码的机会 | 🔴 高 | L2-L6 全部课程 |
| P3 | 练习题量严重不足，每课仅3道 MiniQuiz | 🟡 中 | L2-L6 |
| P4 | 无难度分层，同一份材料同时给刚入门和已经会写的学生 | 🟡 中 | 全部课程 |
| P5 | Python 进阶项目内容深度不均（Sorting 2229行 vs FileOps 398行） | 🟢 低 | Python 进阶 |

### 改进建议

**P1 — 扩充 L3-L6 课程内容（最优先）**

利用现有的 LessonShell 框架和 laeb 组件，为 L3 前4课做示范性内容扩充：
- 每课增加 3-5 个「概念拆解」段落（用生活类比+图示）
- 编程题从「只有MiniQuiz」升级为「MiniQuiz + CodeBlock示例 + 编程挑战」
- 参考 L1 的叙事风格：每个概念先讲故事/场景，再给代码

**P2 — 嵌入在线编程环境**

最简单的方案：在 CodeBlock 旁边加一个「试一试」按钮，点击展开一个可编辑的 textarea，学生修改代码后点击运行可以看到输出（用前端沙箱 eval 或 iframe 嵌入 JDoodle/OneCompiler）。

**P4 — 引入难度标签**

为每道练习题标注难度（⭐/⭐⭐/⭐⭐⭐），课程页面显示「基础必做」和「挑战选做」分组。

## 二、结构逻辑

### 现状

系统采用 **双层课程架构**：

```
/lesson/:level/:lessonId  →  96课逐课教学（CppLessonShell / L1自定义）
/level1~8                 →  等级冲刺页（标签页式复习中心）
```

另外还有：
- `/python/f1~f7` — Python 基础
- `/python/a1~a2, /python/binary-search, ...` — Python 进阶项目
- `/question-bank/:level/:paperId` — GESP 真题考试

### 优点

- **路由参数化**：`/lesson/:level/:lessonId` 一条路由覆盖96课，比手工写96个Route优雅很多
- **LessonCatalog 统一入口**：C++ 6个等级 + Python 基础/进阶，一张页面呈现全部课程
- **等级冲刺页与课程分离**：课程负责「学」，冲刺页负责「练+复习」，职责清晰
- **LegacyLessonRedirect**：旧URL自动跳转，不破坏已有书签

### 问题清单

| # | 问题 | 严重度 |
|---|------|--------|
| S1 | 课程与冲刺页之间没有双向链接，学生看完课不知道有对应冲刺页 | 🟡 中 |
| S2 | L7/L8 只有冲刺页（CourseLevel7/8），没有对应的 `/lesson/7/x` 课程 | 🟡 中 |
| S3 | Python 课程与 C++ 课程之间没有学习路径桥接说明 | 🟢 低 |
| S4 | LessonCatalog 的 unavailableLessonIdsBySection 为空对象，未标记哪些课未上线 | 🟢 低 |

### 改进建议

**S1 — 课程↔冲刺页双向链接**

在每课的 LessonNextSteps 或最后一节底部，自动添加「前往L{n}冲刺复习 →」链接。同样在冲刺页添加「返回逐课学习」链接。

**S2 — L7/L8 课程规划**

如果短期内不打算开发 L7/L8 的96课内容（这个工作量确实巨大），至少在 `/level7` 和 `/level8` 页面标注「本等级暂无逐课内容，以下为冲刺复习资料」，避免用户困惑。

## 三、用户学习路径

### 现状

**入口发现**：首页 → LearningPaths → LessonCatalog（课程目录页）。用户进入目录后看到8个课程板块，点击进入某一课。

**导航**：
- 课程内有「上一节/下一节」「上一课/下一课」导航
- CppLessonShell 的侧边栏展示5个分节
- 每课最后一节有「下一课衔接」Callout

**进度追踪**：
- 考试有 examProgress.js（localStorage 保存答题进度）
- **课程学习进度：无任何追踪**

### 问题清单

| # | 问题 | 严重度 |
|---|------|--------|
| L1 | 完全没有学习进度追踪，用户不知道学到哪了、哪些课还没看 | 🔴 高 |
| L2 | 没有「推荐下一步」的个性化引导，所有用户看同一张课程目录 | 🟡 中 |
| L3 | 课程目录无「已完成/进行中/未开始」状态标记 | 🟡 中 |
| L4 | 没有搜索功能，用户无法按知识点关键词找到对应课程 | 🟢 低 |
| L5 | 没有学习目标设定（如「本周完成L3前5课」） | 🟢 低 |

### 改进建议

**L1 — 实现最简学习进度追踪（最高优先级）**

用 localStorage 记录每课的「已访问」状态和每节课最后访问的分节编号。在 LessonCatalog 中展示：

```jsx
// 极简实现（< 50行代码）
const [progress, setProgress] = useState(() => {
  return JSON.parse(localStorage.getItem('gesp-lesson-progress') || '{}');
});
```

在课程页面加载时自动记录，在目录页显示状态图标（✓已完成 / ●进行中 / ○未开始）。

**L2 — 课程目录加「继续学习」入口**

在 LessonCatalog 顶部添加一个横幅：「继续学习 → L3 第5课 · 一维数组的奥秘」，自动跳转到用户上次访问的课程。

**L3 — 课程目录状态标签**

为每个等级板块的 16 节课增加小圆点状态指示器。

方案选择（按实现难度排序）：

| 方案 | 实现成本 | 效果 |
|------|----------|------|
| iframe 嵌入 JDoodle/OneCompiler | 1天 | 完整C++/Python编译运行 |

2. 学生输入答案后点「提交」
3. 判断对错，显示解析
4. 记录结果

改动量约 30 行代码。

**I6 — AIChatWidget 感知课程上下文**

将当前课程ID和分节ID作为 context 传给 AI 对话框，使 AI 能回答「帮我解释一下刚才讲的按权展开」。

## 六、技术性能

### 现状

**构建产物**: 总大小 9.5MB，473个JS文件。

**代码分割策略**：
- vendor-react (React/ReactDOM/Router)
- vendor-markdown (337KB)
- vendor-katex (255KB)
- vendor-motion (122KB)
- 课程页面全部 lazy() 加载
- 试卷数据通过 getPaper() 动态 import

**首屏加载**：使用了 DeferredSection（IntersectionObserver延迟加载），LessonCatalog、FeaturedProjects等组件滚动到视口才加载。

**index.html**：有完整的 SEO meta 标签、OG 标签、Google Analytics。

### 问题清单

| # | 问题 | 严重度 |
|---|------|--------|
| T1 | 总bundle 9.5MB偏高，主要来自 93 份试卷数据（每份40-60KB） | 🟡 中 |
| T2 | vendor-katex (255KB) — KaTeX 数学渲染库，如果仅少量试卷有数学公式，属于过度加载 | 🟡 中 |
| T3 | 93 份试卷各为一个独立chunk，但没有任何预加载/预取策略 | 🟢 低 |
| T4 | 没有 Service Worker 或离线缓存策略 | 🟢 低 |
| T5 | 缺少图片懒加载（如果未来添加更多示意图） | 🟢 低 |
| T6 | 字体策略：JetBrains Mono 和 PingFang SC 依赖系统字体，无webfont fallback问题 | ✅ 已处理好 |

### 改进建议

**T1 — 试卷数据进一步优化**

93份试卷共约5MB，是bundle大小的主要贡献者。可考虑：
- 将大部分旧试卷（2023-2024）的 `explanation` 字段进一步精简
- 或按需加载试卷列表时不预加载任何试卷数据（目前 QuestionBankHome 已优化为只读 paperMeta）

**T2 — KaTeX 按需加载**

仅在包含数学公式的试卷中动态 import KaTeX，而不是作为全局 vendor chunk。可以通过检查试卷内容是否包含 `$` 或 `\\(` 来判断。

**T4 — 添加 Service Worker**

因为是纯静态站（GitHub Pages），适合添加 Workbox 生成的 Service Worker，实现：
- 已访问页面的离线可用
- 静态资源的缓存优先策略
- 减少重复访问的加载时间
