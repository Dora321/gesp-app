第14课 决策段 8–24 分

对照设计图，逐字问

决策段 · 在原代码上加：「在我上节课的代码基础上（读光敏值 value），请加上决策：如果 value 低于 1000 就点亮 GPIO2 的 LED，否则熄灭它。约束：沿用我原来的变量名，带中文注释，只改必要的部分。」
完整全码 · 主线：智能小夜灯（感知＋决策＋执行）
from machine import Pin, ADC       # 引脚与模拟读取工具
import time                        # 时间工具

light = ADC(Pin(34))               # 感知：光敏接 GPIO34
light.atten(ADC.ATTN_11DB)         # 量程 0~3.3V
led = Pin(2, Pin.OUT)              # 执行：LED 接 GPIO2

THRESHOLD = 1000                   # 决策阈值：低于它算天黑

while True:
    value = light.read()           # 感知：读亮度
    if value < THRESHOLD:          # 决策：如果很暗
        led.value(1)               # 执行：亮灯
    else:                          # 否则（够亮）
        led.value(0)               # 执行：灭灯
    print("亮度：", value)         # 顺便显示，方便调阈值
    time.sleep(0.5)

今天的提问和上节课不一样：不是重新要一段，是在原来的基础上加。

看开头那句：「在我上节课的代码基础上（读光敏值 value）」。

括号里为什么要写变量名？因为 AI 不知道你上节课的变量叫什么。你不说，它自己起一个新名字，两段代码就拼不到一起了——这是今天最常见的翻车。

三条约束也很关键。

「沿用我原来的变量名」——防止它改名。

「只改必要的部分」——这就是第 6 课学的追问话术③，防止它把整段重写。

看代码。和上节课比，多了什么？

多了一行 THRESHOLD = 1000，还有循环里那个 if / else。

就这两处。其他一行没动——这就是「只改必要的部分」的效果。

特别注意 else 分支里的 led.value(0)。

少了它会怎么样？灯亮了就再也不灭。因为没人告诉它什么时候关。

这是今天第二常见的翻车。

第14课 附录范例 8–24 分

温度组：完整作品

感知（DHT11）→ 决策（超过 30 度）→ 执行（屏显 ＋ 蜂鸣报警）

完整全码 · 桌面温度警报器
from machine import Pin, SoftI2C
import dht, time
from ssd1306 import SSD1306_I2C

sensor = dht.DHT11(Pin(14))        # 感知：DHT11
i2c = SoftI2C(scl=Pin(22), sda=Pin(21))
oled = SSD1306_I2C(128, 64, i2c)   # 显示：OLED
buzzer = Pin(13, Pin.OUT)          # 执行：蜂鸣器

LIMIT = 30                         # 决策阈值：超过 30 度报警

while True:
    sensor.measure()               # 先测一次
    t = sensor.temperature()       # 取出温度
    oled.fill(0)
    oled.text("Temp: " + str(t) + "C", 0, 0)
    if t > LIMIT:                  # 决策：温度过高
        oled.text("ALARM!", 0, 20)
        buzzer.value(1)            # 执行：报警
    else:
        buzzer.value(0)            # 否则安静
    oled.show()
    time.sleep(2)

做温度警报器的组看这一页，完整版。

结构和主线一样，三段清清楚楚：

感知——DHT11 读温度。

决策——if t > LIMIT，超过 30 度就报警。

执行——屏幕显示 ALARM，蜂鸣器响。

注意这里比夜灯多一样：执行段有两件事（屏显和蜂鸣），所以 if 里面有两行、else 里面也要照顾到。

看 else 那支：buzzer.value(0)——把蜂鸣器关掉。

这一行要是少了，蜂鸣器一响就停不下来，整个教室都会恨你。

还有一个细节：oled.show() 放在 if/else 外面。为什么？

因为不管报不报警，屏幕都要刷新。把它放在外面，两种情况都能显示。

这就是组装的功夫——哪一行放在哪一层缩进里，是有讲究的。

第14课 AI 出错时刻 50–62 分

判断方向反了

天亮反而亮灯，天黑反而灭灯——代码不报错

AI 写的决策段
THRESHOLD = 1000

while True:
    value = light.read()
    if value > THRESHOLD:      # 方向反了！
        led.value(1)
    else:
        led.value(0)

# 结果：天亮反而亮灯，天黑反而灭灯

病因：大于写成了小于的反面

我的设计图写的是「暗了才亮」，也就是读数小于阈值。AI 写成了 value > THRESHOLD——方向整个反了。

怎么抓：对照设计图逐字核对

你图上写的是「如果很暗就亮灯」→ 「很暗」＝ 读数小→ 所以必须是 <。
AI 也会搞反，你得当那个把关的人。

这又是一个不报错的错——只能靠遮一下来发现：遮住反而灭了，就是方向反了

看这段 AI 写的决策。它写的是 if value > THRESHOLD。

运行——不报错。灯也会亮会灭，看起来挺正常。

但是你一遮光敏，灯反而灭了；一开灯，它反而亮了。

整个反的。

病因在哪儿？我的设计图上写的是「暗了才亮」。

「暗」意味着读数小。所以代码应该是小于阈值。AI 写成了大于——方向反了。

这种错怎么抓？对照设计图逐字核对。

你图上写的是「如果很暗就亮灯」。那就一个词一个词地对：

「很暗」是什么？读数小。那代码里应该是大于号还是小于号？小于。

这是今天我要你们记住的一句话：

AI 也会搞反，你得当那个把关的人。

第 5 课我们学的三类错误，还记得最难的一类吗？逻辑错——不报红字，但结果不对。

现在讲今天最实用的东西：联调排错三步法。

先给你们打个预防针：联调不工作，很正常。

三块积木各自都跑得好好的，一拼起来就不动了——这是每个工程师的日常。别慌，别乱改代码。

按这三步查。

第一步，测感知。 把决策和执行先不管，单独打印传感器读数。还读得到吗？数值随环境变吗？

不变，问题在感知段，回 L13 那页查。

第二步，测决策。 打印判断结果——比如在 if 里面加一句 print("该亮了")。

遮住光敏，这句话打出来了吗？没打出来，说明条件根本没成立，是阈值不对或者方向反了。

第三步，测执行。 单独让灯亮一下、蜂鸣器响一下，确认它本身没坏、线没松。

三段都查过了还是不动？那问题就在「拼」的地方。

最常见的是什么？——变量名对不上。上节课叫 value，这节课 AI 给你写成了 light_value。

所以我刚才才反复强调那句约束：「沿用我原来的变量名」。

第14课 联调 62–76 分

阈值怎么定？先打印，再定

不要凭感觉填一个数——用真实读数定

1
先让程序打印读数，记下两个数：开灯时多少、手遮住多少
2
举例：开灯 3000，遮住 500 → 阈值取中间，定 1500 左右
3
改完上传，遮一下试试：该亮的时候亮了吗？该灭的时候灭了吗？
4
一直亮 / 一直不亮 ＝ 阈值离谱了，回头看打印的数再调
5
代码里留着那行 print(...)——调阈值时它是你的眼睛
教室里各组的读数不一样（靠窗的亮、墙角的暗），所以阈值也不该一样——这就是为什么要自己测

阈值这件事，我看到好几组直接填了 1000——因为我 PPT 上写的是 1000。

别抄。 1000 是我的教室、我那个位置的数。

正确的做法是：先打印，再定。

第一步，让程序打印读数，记两个数：开灯的时候读到多少？用手遮住读到多少？

比如你记下来：开灯 3000，遮住 500。

第二步，取中间。3000 和 500 中间是 1750，那你定 1500 或者 1800 都行。

第三步，改完上传，遮一下试试。该亮的时候亮了吗？该灭的时候灭了吗？

如果一直亮或者一直不亮，说明阈值离谱了，回头看打印的数重调。

还有一条实用的：代码里那行 print 先留着，别删。

调阈值的时候，它就是你的眼睛——你能看见此刻读数是多少，一眼就知道阈值该往哪边挪。

最后说一句有意思的：靠窗的组和墙角的组，读数天差地别。

所以你们的阈值本来就不该一样。 这就是为什么必须自己测。
